# Second sync: web `2119f3d` → `9c52496`

The first parity pass (`docs/aakash-gochar-parity.md`) closed the gap as of
`2119f3d`. Web kept moving — ~40 commits, 79 files, ~7,445 lines across
`sky3d`/`learn`/`gochar` — before this pass started. This is that pass's
record.

## What was actually new (not i18n churn)

Verified by reading diffs, not by line-count stats — most of the "big diff"
Learn components turned out to be a single web-only i18n-catalogue migration
(`toNepaliDigits`/hardcoded bilingual strings → `react-i18next`), with no
geometry or behavior change. Mobile's own i18n (`useLocale`/`pick`) already
covers the same ground its own way, so none of that needed porting.

The genuine feature gaps, and what happened to each:

## Server/client split

Checked, and unchanged from the architecture `docs/3d-sky.md` already
documents: the server computes positions (sidereal ecliptic longitudes,
`vedic_stars`), the client only projects and renders. None of this pass's
new web modules compute real astronomy on the client — `terrain.ts` is a
seeded PRNG for decorative hillside geometry, `vedic-constellations.ts` is
static topology over already-catalogued stars, `horizon-projection.ts` /
`grid-labels.ts` / `sky-zoom.ts` are pure projection/UI math. The only
server-shaped change was `vedic_stars` itself, which the server already
sent — mobile just wasn't parsing it.

## Kept for a later pass

Wiring `toggles.vedicStars` + drawing the named stars as points in the scene
is the piece that would make `vedic-constellations.ts` and the search
result's "aim at a वैदिक तारा" both fully payoff — right now search can name
and aim at them, but the scene has nothing to draw there yet.
